# Deploy 重构实现依据

确认日期：2026-10-15（Asia/Shanghai）。状态：本次范围已实现并完成定向回归与授权真实交互验收；实现结果、证据与验证边界见第 16–17 节。

本次重构将 Deploy 接入右侧任务 Tab 容器，用稳定的部署身份关联历史消息、部署记录、阶段日志和模型运行。AI 继续负责发布讨论、阶段推进、问题诊断与修复，后端负责持久化事实、顺序校验、授权和执行结果。模型文字、决策与审批统一留在中间 Agent 会话区域。

第 2–15 节保存确认的实现要求；功能路由描述当前行为，源码决定实际运行方式。当前实现及验收结果分别记录于第 16–17 节，不能把未实测平台或场景外推为通过。后续用户明确修订决定时，同步修订本文。

早期讨论中“只修订失败阶段、先前成功阶段不会重做”的方案，已经被本轮“允许模型重新执行较早阶段，并使下游结果失效”的决定覆盖。不能恢复旧限制。

最初的文档整理未修改业务代码。用户随后授权按本文实施，并授权独立 Java 项目的真实交互验收；未经额外要求不提交或发布。实现可自行确定模块、字段、事件与工具的最终名称及物理表结构，无需为普通工程选择重复询问用户。

## 2 目标与范围

- 将 Deploy 状态页面迁入现有右侧任务 Tab 容器，复用停靠、放大、收起和页面保留能力。
- 将一次部署作为正式历史消息关联到独立部署记录，支持刷新、重新进入会话和历史回显。
- 后端明确保存当前 Session 的部署模式、部署身份、当前阶段和阶段结果。
- AI 持续掌控阶段推进与问题处理；后端通过工具边界实施 harness。
- 保留 Profile、计划校验、目标身份复核、Guard、沙盒、普通审批和人工 Full Access 例外等已有约束。
- 保留历史数据兼容读取；不新增通用工作流引擎、多任务并行调度或跨后端重启的自动续跑能力。

当前 Session 同时最多一条活动部署；继续保留同一 Workspace 的部署执行互斥。通用容器具备多个 Tab 的展示能力，不代表部署与聊天获得独立并行执行通道。

## 3 重构前行为与目标的主要差异

此表保存重构前的核查结果，不能当作当前仍然存在的问题。后续维护须重新读取当前源码；最终实现见第 16 节。

| 重构前行为 | 本次目标 | 主要入口 |
|---|---|---|
| 右侧只接入 Terminal，Deploy 面板在聊天滚动区 | Deploy 成为右侧任务页 | `chat-console.tsx`、`features/task-container/` |
| 根据时间戳混入部署卡片，并把关联模型消息归组到卡片 | 消息表保存正式部署入口；模型文字统一显示在 Agent 区 | `chat-timeline.tsx`、`deployment-history.ts` |
| `deployment_runs` 的 JSON 快照保存计划、阶段与日志 | 复用并重构独立部署记录，明确历史消息关联及日志追加语义 | `domain/deployment.ts`、SQLite Deployment Repository |
| 阶段完成或失败后，再次调用返回原结果；修订仅针对失败阶段 | 允许明确重跑同一阶段或较早阶段；校验下游失效与前序条件 | `DeploymentService.executeStageForAgent()`、`decideRecovery()` |
| 阶段开始和修订批准时会清空当前阶段日志，日志保留限长尾部 | 同一阶段保留失败输出并追加后续执行日志，支持历史回显 | `DeploymentService.stage()`、`log()` |
| 部署工作流通过不可用占位 Tool 保留定义，并禁用部分普通工具 | 普通工具按原模式可用；部署专用定义按 Session 模式动态加入、移除 | `chat-agent-runtime-factory.ts` |
| 正式构建用部署服务内独立的 `runLocalBuild()` 启动 shell | 代码层复用现有 bash 执行能力，模型侧使用部署语义与数据结构 | `deployment-service.ts`、`harness/tools/bash.ts` |
| 执行 Chat Run 提前结束可能把部署结算为失败 | 部署生命周期跨 Chat Run，由明确的结束动作结算 | `chat-service.ts`、`chat-run-executor.ts` |
| VERIFY 完成时服务直接标记部署成功 | 模型请求成功结束，后端核验全部必要阶段再结算 | `DeploymentService.executePlannedStage()`、`finishAgent()` |

现有阶段执行顺序、重复调用合并、目标校验、SQLite 条件更新与修订审计能力应优先复用，不另建相互竞争的状态源。

## 4 从配置到部署结束的目标流程

1. 用户打开 `/deploy`，发现当前项目内适用于 Workspace 的部署文档与服务。
2. 文档或目标服务缺失时，进入配置讨论，检查项目并补齐标准 Profile。已有其他服务不应阻止补充新服务；保存配置本身不自动执行发布。
3. 用户选定服务、开始本次部署讨论时，创建稳定部署身份与历史消息入口，并绑定当前 Session 的部署模式。单纯打开菜单或浏览配置不创建新的部署行为记录。
4. AI 检查项目、Git 变化和依赖，讨论本次发布范围，提交准确构建步骤、产物、上传目标、重启与验证参数。
5. 后端校验，用户在中间 Agent 区审阅计划并完成必要审批。
6. AI 调用部署接口逐阶段推进，后端执行并发布阶段和日志事件；问题发生后继续诊断、修复或重做阶段。
7. 用户退出，或模型明确请求成功、失败结束；后端统一结算，退出部署模式，并保留完整历史入口和执行记录。
8. 模型最终结论在中间 Agent 区显示。

配置讨论与本次发布讨论是不同用途。Profile 保存长期知识，本次计划保存本次发布准确参数；不能直接把 Profile 的说明或历史命令当成本次已批准计划。

讨论、执行和修复需要沿用同一个部署身份；一个部署可关联多个 Chat Run。是否合并现有 Discussion/Run 表或通过关联实现这一身份，属于工程设计。

## 5 历史消息与部署记录

### 历史中的部署入口

- 一次部署在历史信息记录表中保存一条结构化部署行为消息，关联部署 ID、Session、稳定标题和历史顺序。
- 用户点击该消息，打开或定位右侧对应 Deploy 页面。历史部署可以只读回显，不因此进入活动部署模式。
- 阶段变化更新入口的状态展示，不为每条日志或每次阶段变化插入新的聊天消息。
- 标题与消息位置稳定；实时状态以部署记录为准，不复制出另一套可独立变更的部署事实。
- 沿用 Session 内消息 `sequence` 的排序能力，避免继续仅按两个数据源的时间戳猜测历史位置。
- 新部署行为消息必须贯通领域类型、SQLite、消息 API、SSE、前端归约和历史渲染。

历史展示与模型上下文分别投影。部署消息不是用户的新指令，UI 数据与完整日志不能直接作为 user 消息交给模型。当前通用 `custom` 消息会在 `convertToLlm()` 中转成 user 消息，实施时需显式处理部署消息。

### 独立部署事实与日志

| 数据 | 职责 |
|---|---|
| 部署记录 | 保存服务、目标、本次有效计划、整体状态、时间和结束原因 |
| 阶段记录 | 保存稳定阶段身份、当前结果、命令、有效版本与执行事实 |
| 执行记录 | 区分同阶段各次实际执行，用于输出归属、取消、请求幂等和结果审计 |
| 日志 | 按部署、阶段、执行身份与顺序追加，支持实时订阅与历史读取 |
| Chat 消息 | 保存模型回复、追问、诊断、修复说明与最终结论，并关联部署身份 |

现有 `deployment_runs` 已是独立部署表，应评估复用。日志、阶段和执行记录是否拆表由实现确定；不为满足概念命名再建立一套含义相同的状态表。

后端需输出当前阶段、步骤、产物、真实字节进度、执行结果等结构化事实。前端不能解析模型文字来推断部署状态，也不能用日志文本代替正式状态字段。

## 6 Session 部署模式与退出

后端持久化 Session 是否处于部署模式，以及绑定的部署 ID、当前阶段、阶段状态和必要的并发版本。字段名称与是否使用独立关联表不预先固定。

部署模式跨 Chat Run 保留。等待用户输入、审批、模型诊断、阶段失败或模型一轮回复结束，都不自动结束部署。前端刷新、离开会话、关闭或收起 Deploy 页不改变后端模式。

### 三类业务退出

| 场景 | 发起方式 | 终态 |
|---|---|---|
| 用户手动退出 | UI 调用后端退出接口 | `cancelled`，表示主动中止 |
| 模型完成所有流程 | 模型调用部署结束工具，提交成功结果 | `success`，须通过后端核验 |
| 模型认为无法完成，或用户明确同意、要求以失败结束 | 模型结束工具或用户结束接口，记录原因 | `failed` |

用户单纯点击退出与明确要求“本次失败，结束部署”需要区分。阶段失败先停留在部署模式中，允许诊断与修复；不能立即当作整体失败退出。

用户入口和模型入口共用一个后端结束用例，顺序为：

```text
校验部署身份、当前状态与结束请求
  → 收敛仍在执行的部署操作，保存实际结果和可能已发生的副作用
  → 持久化最终结果、原因与阶段事实，清除 Session 活动部署绑定
  → 使部署专用工具失效并从后续模型请求移除
  → 发布部署结束事件，更新历史入口与右侧 UI
```

- 成功请求只能在当前有效计划的必要阶段全部成功或按计划合法跳过后通过；否则返回未满足条件，保留部署模式。
- 失败结束记录原因和已经完成的实际阶段，不能只保存一个失败布尔值。
- 结束接口幂等；用户退出与模型结束竞争时，通过原子状态转换确定一次终态，后续请求返回已保存结果。
- 结束后的迟到工具请求、输出和异步回调不得重新激活部署或覆盖终态。
- 结算持久化失败时保留可重试的结算事实，不能先声称结束成功，或重新执行已发生副作用的阶段。

进程中断属于运行恢复路径，与上述业务退出原因分别处理。保持现有保守边界：不伪造旧进程仍存活，不重放命令，不恢复进程内一次性授权；恢复时核对持久化事实并明确中断原因。不得把浏览器断线当成后端部署失败。

## 7 阶段推进与上游重做

阶段展示沿用准备、构建、上传、重启、验证。讨论和等待确认是部署行为的过程状态，不能在尚无实际计划时伪造已完成的执行步骤。

模型通过部署接口请求执行、重跑或切换阶段；后端根据真实执行结果写入阶段状态。模型不能直接把未执行阶段声明为成功。

| 当前情况 | 请求 | 处理 |
|---|---|---|
| 构建失败 | 再次执行构建 | 原构建阶段重跑，日志追加 |
| 重启失败，发现产物问题 | 执行构建 | 允许重做构建；上传、重启、验证重新等待执行 |
| 验证发现上传问题 | 执行上传 | 校验当前产物与计划后允许；后续重启、验证重新等待执行 |
| 构建成功，上传未完成 | 执行重启 | 拒绝跨阶段推进，返回当前允许的下一阶段 |
| 构建仍在执行 | 执行上传或另一构建请求 | 按执行身份去重或返回忙，不并行启动其他阶段 |
| 任一部署过程 | 普通工具诊断 | 按原工具规则执行，不据此推进或结算部署阶段 |

重新执行较早阶段本身表达回退意图，不增加专门的“退回阶段”工具。上游重做后，下游旧结果、产物版本与授权不能继续被当作本次有效结果；历史输出与结果仍保留用于审计。

同一部署内的阶段副作用串行。当前操作需先结束或取消，才能启动其他阶段。重发同一执行请求应返回或附着原执行；新的明确执行请求才产生重跑，避免网络重试导致重复构建、上传或重启。

重做构建与恢复旧版本是不同操作。本次不增加自动回滚、版本切换或自动补偿已发生远端副作用的能力。

## 8 同一阶段的日志持续追加

阶段身份保持不变。修复和重跑始终应用于原阶段，不创建“构建 2-1”、子阶段或第二条同名阶段。UI 不以新增阶段节点表达执行次数。

旧失败输出保留，新输出在原阶段日志中 append。可以用一行时间与“重新构建”等简短执行边界区分，例如：

```text
14:32:10 开始构建
14:32:26 [ERROR] 缺少依赖
14:32:26 构建失败，退出码 1
14:35:08 重新构建
14:36:20 [INFO] BUILD SUCCESS
```

后端仍保存每次执行的身份、开始/结束时间、结果与日志归属，但这些记录不会扩张成 UI 阶段树。阶段当前状态代表最新有效执行，不能因保留旧失败日志而继续显示已修复的旧失败状态。

日志应具备稳定顺序和读取游标。实时增量与 REST 历史补齐要能去重，并拒绝把旧执行的迟到输出归到新执行中。不能在重试时清空日志，或把一次累积输出快照当作增量反复 append。

完整历史保留、存储上限和分页策略由实现明确；若需要截断，必须保留可见截断事实。模型结果可返回限长尾部，但不能因此丢弃用户需要回显的持久化日志。

## 9 工具复用与模型 harness

### 部署工具与现有 bash 的代码复用

- 正式构建向模型暴露部署语义的接口和参数，执行结果属于部署数据结构。
- 代码层复用当前 bash 的底层执行能力，包括工作目录、命令运行、输出采集、取消与超时；避免长期保留两套独立进程实现。
- 当前 bash 使用 `executeShellWithCapture()`，正式部署构建另用 `runLocalBuild()`，实施时核对并收敛两条链路。
- 本地构建发生在 Gori 后端所在机器；远端执行继续复用 SSH 命令运行时。不能把远端 Terminal 沙盒当成本地构建的隔离边界。

### 普通工具保持可用

部署中的模型仍可正常使用当前交互模式已有工具，包括 Terminal Mode 下的 `terminal_interaction`，用于检查 Linux 服务器、项目、文件和依赖等信息。

保留普通工具原有沙盒、Guard、审批、模式和生命周期规则，不因为处于部署状态而额外整体禁用 SFTP、Terminal 等已有能力。当前部署工作流的专门禁用分支需要据此调整；正常模式限制仍有效。

普通工具结果不直接更新部署阶段进度或结算阶段成功。正式任务推进通过部署接口记录。不能依靠匹配 shell 命令字符串可靠判定所有操作是否只读；不新增未经确认的诊断权限模型。

### 仅在部署模式注入专用工具

- Session 进入部署模式后，相关部署工具加入模型可用的真实工具集合。
- Session 未处于部署模式或已结束时，不再向模型暴露这些定义，不能只保留 `unavailableTool` 占位定义。
- 工具执行入口再次读取并校验部署模式、绑定身份与版本，处理旧上下文、迟到调用和退出竞争。
- 部署模式跨 Chat Run 恢复时，重新根据后端事实装配工具，不依赖前端是否显示 Deploy Tab。

### 每次调用同步部署状态

每次工具调用后，包括普通诊断工具，向模型同步最新部署状态；每次请求模型之前，再从后端刷新动态状态。最小内容是当前处于部署模式、当前阶段和阶段是否成功，建议用明确状态表达运行、失败与等待，示意为：

```text
当前处于部署模式。
当前阶段：构建。
阶段状态：失败。
```

状态说明属于可信的模型运行上下文，不生成可见聊天气泡，也不进入右侧执行日志。状态读取不能依赖模型自述，且不能在历史上下文中无界堆积重复说明。提示用于帮助模型保持任务意识，执行许可仍由后端硬校验。

### strict 校验与可修正错误

1. 在副作用发生前严格校验工具 JSON 的必填字段、类型、枚举、大小、未知字段与必要的路径约束。
2. 再校验 Session 模式、部署身份、有效计划、阶段顺序、当前执行及授权。
3. 参数或顺序错误返回结构化、可修正结果，指出错误字段、原因或允许的下一阶段，让模型重新调用。
4. 错误请求不改变阶段、不创建无意义审批、不执行命令；不自动终止整个部署。
5. 数据库、执行环境、探针等内部故障保留原有故障分类，不能统一当作模型 JSON 错误重试。

现有 Agent Loop 的参数准备、Schema 校验、`beforeToolCall` 和非终止型 `AgentToolError` 是可复用入口，需同时覆盖 Agent 调用与服务直接调用的边界。

## 10 计划确认与权限

初次计划仍需用户确认。命令、产物或目标变化后，重新审阅受影响内容；相同命令的阶段重跑不重复确认整份计划，但仍遵守普通审批和 Full Access 例外规则。

- 用户决策工具用于补充信息，不代替部署计划确认或权限批准。
- 人工 Full Access 例外仍绑定准确命令与目标，不能由 `autoAudit` 自动批准；一次性授权消费后不能因重跑而复用。
- 计划、目标身份或沙盒配置变更后，旧授权不得自动扩大或沿用到新副作用。
- 普通工具与部署工具继续使用已有 `autoAudit`、Guard 和远端沙盒政策。
- 初始计划确认、修订确认、普通审批和权限例外的交互统一放在中间 Agent 区域。

不能以“AI 负责修复”为理由删除已有授权边界；也不能把现有独立修复 Run 和旧 UI 的全部编排强加给新流程。保留授权语义，具体工具和衔接方式随重构调整。

## 11 部署专有事件与 Chat 事件

部署执行的状态与日志使用独立业务事件，不能继续让前端依据普通 user/tool 消息猜测阶段。建议语义如下，名称只是示意：

```text
deployment.started
deployment.stage.updated
deployment.log.appended
deployment.finished
```

事件包含部署身份、Session、必要的阶段/执行身份、顺序或版本信息与业务数据；支持刷新后的 REST 补齐。结束事件与最终事实一致，重复或迟到事件不能恢复旧状态。

| 内容 | 通道与前端投影 |
|---|---|
| 部署开始、阶段结果、产物进度、日志追加、部署结束 | 部署业务事件，更新右侧页和历史入口 |
| 模型普通文字、追问、诊断、修复说明、最终结论 | Chat 消息，显示在中间 Agent 区域 |
| 用户决策与审批 | 现有 Chat 交互，关联部署身份，显示在中间区域 |
| 模型 API 内部工具调用与结果 | 保留模型协议要求，后端分别投影到上述业务通道 |

部署专有事件不意味着重写模型厂商的 user/assistant/tool 协议，也不意味着把模型文字搬入部署事件或右侧日志。前端消费事实，不另行编排阶段执行。

## 12 右侧 Deploy 页面与中间会话

### 展示职责

| 中间 Agent 区域 | 右侧 Deploy 页面 |
|---|---|
| 模型计划说明、提问、诊断、修复说明、最终结论 | 服务、目标、整体状态、阶段导航、当前阶段详情 |
| 所有决策、计划确认与工具审批 | 真实进度、产物、退出结果、执行日志 |
| 一条紧凑部署历史入口；必要的工具调用摘要 | 当前部署和历史部署的详细回显 |

右侧不再显示任务模型输出或详细聊天内容。移除当前把部署关联 Chat 消息归组到部署卡片的展示行为；消息仍在原有存储与协议中，不复制、改写模型文字。

### 视觉基线与日志交互

以本次“阶段总览”草案和用户给定的横向阶段设计为实现基线；“阶段侧列”仅为讨论过的备选，不要求实现第二套可切换布局。

- 第一视觉重点是当前处于哪个阶段、阶段是否成功或失败，以及本次部署整体状态。
- 页面保持简洁、干净，沿用项目主题与颜色层次；不要增加解释性段落、宣传空态和冗余指标。
- 保留精简服务标题、目标、阶段导航、当前阶段内容和执行日志，避免 Tab、页内标题与状态反复重复。
- 已经显示上传状态、文件和进度后，不再增加“正在通过 SFTP 上传”“Agent 正在等待”等重复解释。
- 阶段条表示阶段状态，不用已完成阶段数伪装精确总进度。上传百分比来自真实字节数；Maven 构建显示状态和耗时，不编造百分比。
- 允许查看已完成阶段。正在查看的阶段与当前真实运行阶段分别管理，查看旧构建日志时整体状态仍明确显示正在上传。
- 日志提供分组展开、时间戳、跟随输出和错误定位等必要交互；用户主动查看旧日志时不要强制拉回最新位置。
- 同阶段重跑只追加日志，不出现新增阶段、子阶段或“2-1”节点。
- 停靠与放大布局都需要有效利用空间；移入默认宽度 45% 的右栏本身不保证更宽，不能保留聊天卡片的宽度与层层滚动限制来代替页面布局。

参考方向为 Vercel 的视觉克制、Railway 的任务状态表达、Buildkite 的日志交互。官方功能参考：[Vercel 构建日志](https://vercel.com/docs/deployments/logs)、[Railway 部署状态](https://docs.railway.com/deployments/reference)、[Buildkite 日志交互](https://buildkite.com/docs/pipelines/configure/managing-log-output)。这些参考不构成复制其全部功能的要求。

### 放大输入与待处理事项

- 放大仍由现有任务容器管理，覆盖会话主体，不覆盖左侧服务器导航。
- 放大后的 Deploy 页可以提供简洁的“补充部署要求…”输入框，复用同一个 Session 的 Composer 发送、排队与引导链路。
- 发送内容进入原有会话历史，模型详细回复仍在中间 Agent 区；不建立第二套聊天流或在右侧显示聊天记录。
- 有待回复、决策或审批时，放大页提供简短待处理提示和“返回对话”入口，恢复停靠布局并定位原交互，不在右侧复制决策/审批面板。
- 切换 Tab、收起、放大与恢复要保留页面状态、日志位置和输入草稿，不重新启动部署或重复订阅。

Deploy Tab 的关闭只改变展示；明确退出部署使用业务退出入口。不要把 Terminal 的“关闭 Tab 即关闭终端”语义机械套用到 Deploy。活动部署通过入口或历史消息可重新定位；历史记录查看不隐式开启部署模式。

## 13 模块职责与实现选择

| 层 | 职责与边界 |
|---|---|
| 通用 Tab 容器 | 标签、选中、展示模式与关闭请求，不导入 Deploy 业务或调用部署 API |

## 15 验收重点

1. 进入一次部署只产生一个稳定部署身份及正式历史入口，模型多轮讨论、执行、修复保持关联。
2. 配置或目标服务缺失均可补齐；保存 Profile 不自动部署。
3. 刷新或重新进入 Session 能恢复模式、状态、历史与日志；查看旧部署不会激活部署模式。
4. 模型所有文字与最终结论在中间显示，决策/审批只在中间交互，右侧只投影部署事实。
5. 部署工具只在部署模式出现，结束后定义移除且迟到执行被拒绝；普通工具按原模式可用。
6. 普通诊断工具不会结算阶段，每次工具调用和后续模型请求都能得到最新可信部署状态。
7. 无效 JSON、未知字段和跨阶段推进在副作用前被拒绝，模型收到可修正原因；内部故障不被误分类。
8. 同阶段失败修复和重跑始终使用同一阶段节点，旧日志保留，新日志按顺序追加且不会重复累计快照。
9. 在重启阶段重新构建被允许，随后必须重新上传、重启和验证；旧下游结果不再有效。
10. 执行请求重发幂等，新明确请求可重跑；运行中阶段不与其他部署阶段并行。
11. 修改命令、产物或目标遵守确认规则，Full Access 不自动批准、不复用已消费授权。
12. 用户退出、模型成功结束和明确失败结束分别得到正确终态、原因与事件；结束竞争只确定一次结果。
13. 成功结束无法绕过必要阶段，阶段失败或单个 Chat Run 结束不会自动退出部署模式。
14. 结算失败可恢复且不重放副作用；中断恢复不伪造存活进程或恢复内存授权。
15. Tab 切换、收起与放大不重新启动任务、不丢日志位置或草稿；Terminal 既有行为不受破坏。
16. 放大输入使用同一 Session，待决事项可返回中间区域处理，右侧不出现第二套聊天内容。
17. 以阶段总览为视觉基线，当前阶段清楚、信息克制、进度真实，停靠和窄屏均可阅读日志。
18. 历史数据可兼容读取，功能文档明确反映实际完成范围，不把设计目标写成已实现事实。

## 16 实现与验收结果（2026-10-15）

本次确认范围已落地。工作区同时存在独立统计功能的改动；本次保留其 v29 migration、运行时装配、页面和文档映射，没有提交、推送或发布。

### 最终实现

- v30 `deployment_sessions` 保存稳定部署身份、Session 活动绑定和明确终态。新 Discussion、模式及一条正式 `chat_messages` 部署入口同事务提交；Discussion/Run 共用 ID，历史消息按 sequence 排序。UI 元数据从模型输入和压缩投影中过滤。
- v31 `deployment_stage_executions` 与 `deployment_logs` 保存独立执行和完整有序日志。相同 Agent Run + toolCallId 返回原执行，新调用可以重做；同一部署只有一个 running 执行。同阶段日志追加，不创建 2-1 节点。上游重做使下游当前结果与相关一次性授权失效，保留历史审计。
- `DeploymentModeService` 管模式与统一结算，`DeploymentService` 管计划和副作用，`DeploymentExecutionRecorder` 管执行/日志事实。本地构建复用 `NodeExecutionEnv` 和 `executeShellWithCapture()`，远端继续使用现有 Command Operation / SFTP。
- 部署跨 Chat Run，阶段失败、等待决策或一轮模型结束均不自动退出。用户 cancelled、模型 success、明确 failed 共用结束用例；成功核验必要阶段，竞争只写一次终态。结算失败保留原事实，不重放副作用；重启不复活旧进程或内存授权。
- 专用工具仅在绑定的活动模式装配；结束后移除并拒绝迟到调用。每次工具完成和 Provider 请求前读取可信部署状态，普通工具保留原模式、Guard、沙箱与审批边界。严格 JSON 和阶段预检在审批/副作用前执行，已知请求错误可交回模型修正。离线上下文估算和手动压缩也只计算当前模式所需的部署定义。
- Deploy 已进入右侧 TaskContainer。容器不持有部署业务；Hook 按任务事实、配置/历史目录、SSE adapter、日志存储和显示选择拆分。所有模型文字、计划审阅、决策与审批仍在中间。正式部署消息点击定位右侧，Tab × 只隐藏，业务退出是独立接口。
- 页面保留五个稳定横向阶段；日志按执行分组，支持折叠、跟随、错误定位和分页补读。构建显示真实步骤，上传显示真实字节及 B/KiB/MiB/GiB，不虚构 Maven 百分比。放大页只有同 Session 的补充输入和返回中间交互入口。

### 真实验收与发现的修复

用户明确授权使用阿里云工作区、OpenCode Go / DeepSeek Flash 模型，并允许独立本地 Java 项目。实际模型目录为 DeepSeek V4.1 Flash。测试使用小型 Maven Java HTTP 服务、独立远端目录及仅回环监听的端口；完整主机资料、Session/Run ID 和截图保存在仓库外验收记录，不写入本仓库。

1. 经模型只读检查与配置讨论生成 Profile；配置保存未创建部署模式或执行阶段。选定服务后创建本次部署身份和正式历史入口。
2. 首次正式 Maven 构建因预置的缺分号失败；在中间决策后由模型修复，重新调用同一构建阶段成功。完整构建日志共 119 个唯一、有序 chunk，含失败与成功两个执行分组，失败输出没有丢失。
3. 通过真实 SFTP 上传 3410 字节 JAR，调用正式重启与验证阶段，健康检查返回预期标记；模型明确 `deployment_finish(success)`，后端模式变为 null。
4. 手动退出最初发现部署 cancelled 而 Chat Run 被 Adapter 的取消错误改判 failed，且队列可能继续消费。已修复 Provider 中止归一化和 Turn 结束取消检查；重复真实测试确认 Chat Run cancelled、failure 为空，排队消息取消且未进入正式历史。
5. 模型按用户要求显式 failed 结束另一次部署，保存原因，无计划、构建或上传副作用。四次部署记录各自只有一条正式部署历史消息，最终无活动模式。
6. 在真实失败页刷新后恢复模式、日志和中间待决；关闭 Deploy Tab 后从历史重开不重建部署。Terminal Live 与 Deploy 切换、收起/恢复和放大均保留页面及日志位置；Terminal 工具诊断没有推进部署阶段。
